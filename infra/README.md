# Hosting: S3 and CloudFront

The web app is a static site. `npm run build` writes plain files to `out/`;
they live in a private S3 bucket and CloudFront serves them on the app domain.
There is no Next.js server, no Lambda and no Vercel.

| Environment | Address                      | AWS account    |
| ----------- | ---------------------------- | -------------- |
| dev         | `https://app-dev.ambrace.in` | `798299234172` |
| prod        | `https://app.ambrace.in`     | `074259854866` |

Region: `ap-south-1` (Mumbai). The one exception is the TLS certificate, which
CloudFront only reads from `us-east-1`.

## What this stack creates

| Resource                | Name                                 | Purpose                                                                |
| ----------------------- | ------------------------------------ | ---------------------------------------------------------------------- |
| S3 bucket               | `ambrace-<env>-web-<account_id>`     | The site's files. Private; only this distribution can read it.         |
| CloudFront distribution | (ID generated by AWS)                | Serves the site over HTTPS on the app domain.                          |
| Origin access control   | `ambrace-<env>-web`                  | Lets CloudFront, and nothing else, read the bucket.                    |
| CloudFront Function     | `ambrace-<env>-web-clean-addresses`  | Maps `/viva` to `viva.html`. Code: `functions/clean-addresses.js`.     |
| Response headers policy | `ambrace-<env>-web-security-headers` | HSTS, content security policy and the rest. See `security_headers.tf`. |
| SSM parameters          | `/ambrace/<env>/web/hosting/*`       | Bucket name, distribution ID and expected headers, for the pipeline.   |

Cost: CloudFront's always-free tier covers 1 TB and 10 million requests a
month, and the bucket holds a few megabytes. There is no WAF, no Route 53 and
no access logging, because each of those is charged.

## What comes from elsewhere

Both come from `ambrace-backend`, and both must exist before this stack plans.

- **The deploy role, the state bucket prefix and the certificate** are created
  by `infra/bootstrap` there, by an admin, by hand. A pipeline must never be
  able to write its own permissions.
- **The build's settings** (`/ambrace/<env>/web/app_url`, `api_base_url`,
  `cognito_user_pool_id`, `cognito_client_id`, `cognito_domain`) are written by
  the backend deployment (`infra/app`), so they are never copied by hand.

## Where settings and credentials live

The web app has no secrets. Every `NEXT_PUBLIC_*` value ends up in JavaScript
that any browser downloads.

| What                                  | Where                                         |
| ------------------------------------- | --------------------------------------------- |
| API address, app address, Cognito IDs | SSM, `/ambrace/<env>/web/`                    |
| Bucket name, distribution ID          | SSM, `/ambrace/<env>/web/hosting/`            |
| AWS access for the pipeline           | Nowhere. A one-hour role through GitHub OIDC. |
| Role ARN, region                      | GitHub Environment variables (not secrets)    |
| AWS account ID                        | `<env>.tfvars`, in this folder                |
| Your laptop                           | `.env.local`, never committed                 |

## Connect GitHub (once per environment)

See "The web app's pipeline" in `ambrace-backend/infra/bootstrap/README.md`. It
creates the GitHub Environment and sets `AWS_DEPLOY_ROLE_ARN` and `AWS_REGION` on
it. The account ID is not stored in GitHub: the pipeline reads it from
`<env>.tfvars` and stops if the role it was given belongs to another account.

## First deployment of an environment

1. Apply the bootstrap stack in `ambrace-backend`. It prints the certificate's
   validation record (`app_certificate_validation_records`).
2. Add that CNAME record at the DNS provider and wait until the certificate
   shows as issued in ACM (`us-east-1`).
3. Deploy the backend once, so the build's settings are in SSM.
4. Run **Deploy Development** with `PLAN`, read the plan, then `APPLY`. The
   run's summary prints the CloudFront address.
5. At the DNS provider, make the app domain a CNAME to that address.
6. Run **Deploy Development** with `PUBLISH`.

After that, a new version of the site is one `PUBLISH`. `PLAN` and `APPLY` are
only needed when a file in this folder changes.

Production is the same with **Deploy Production**, which only runs from the
`release` branch and waits for a reviewer.

## How a publish works

1. A job with AWS access reads the settings from SSM. It runs no npm code.
2. A job with **no** AWS access installs dependencies and builds the site.
3. A job with AWS access uploads `out/`, refreshes CloudFront and checks the
   live site. It runs no npm code either.

Files under `_next/static/` have a hash in their name. They are uploaded first,
cached for a year, and kept for 30 days after the last build that used them, so
a student who is in a viva during a publish is not left with missing files.
Everything else is uploaded with "ask every time", so a new page is seen on the
next load.

## Content security policy

Dev enforces it (`enforce_content_security_policy = true` in `dev.tfvars`).
Prod is still report-only: the browser logs what it would have blocked and
blocks nothing. Once sign-in and a full viva run with a clean console on dev,
set it to `true` in `prod.tfvars` and `APPLY`.

When the browser needs to talk to a new origin, add it to `connect_sources` in
the var file.

## Telemetry (PostHog)

Off until a key is set. To turn it on for an environment, create the String
parameter `/ambrace/<env>/web/posthog_key` in SSM (a PostHog project key is
public) and `PUBLISH`. `/ambrace/<env>/web/posthog_host` is optional and
defaults to `https://us.i.posthog.com`, which is already in `connect_sources`;
a different host must be added there too.

## Try it without AWS

```powershell
npm run build
```

```powershell
npm run preview
```

`preview` serves `out/` on `http://localhost:3000` using the same address
function that ships to CloudFront, and answers a missing file with `404.html`.

```powershell
terraform -chdir=infra test
```

The Terraform tests use a mock AWS provider and need no credentials.
